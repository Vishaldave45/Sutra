# Conversation Domain Architecture & Model

This document outlines the architectural boundaries, persistence guarantees, and data models of Sutra's Conversation domain (implemented in Phase 3).

---

## 1. Core Concepts & Separation of Concerns

Sutra strictly separates the persistent communication record from runtime execution contexts:

```text
Conversation (Durable, persistent chat history)
    │
    └── Messages (Individual turns: user, assistant, system)

[FUTURE CONCEPTS - NOT IN PHASE 3]
Session      (Temporal transport/client connection state)
AgentRun     (A discrete reasoning execution pass of the agent)
```

- **`Conversation`**: The container for a sequence of interactions. It owns the conversation identity (`id: UUID`), creation/update timestamps, and channel/context `metadata`.
- **`Message`**: An atomic communication turn belonging to exactly one conversation.
- **`AgentRun`** (Phase 5): An in-memory or execution-specific record of an agent invocation. It is **not** a Conversation and is not a Message.

---

## 2. Data Model & Schema

### `conversations` Table
- `id`: UUID (Primary Key, autogenerated).
- `created_at`: TIMESTAMPTZ (Non-nullable, indexed via `ix_conversations_created_at`).
- `updated_at`: TIMESTAMPTZ (Non-nullable, indexed via `ix_conversations_updated_at`).
- `metadata`: JSONB (Default `{}`). Used for non-relational context such as channel tags (`whatsapp`, `web`, `api`), client identifiers, or external session references.

### `messages` Table
- `id`: UUID (Primary Key, autogenerated).
- `conversation_id`: UUID (Foreign Key -> `conversations.id` `ON DELETE CASCADE`, indexed via `ix_messages_conversation_id`).
- `role`: Native PostgreSQL Enum `message_role` (`user`, `assistant`, `system`).
- `content`: TEXT (Non-nullable). Must contain non-empty, non-whitespace text.
- `created_at`: TIMESTAMPTZ (Non-nullable).
- `metadata`: JSONB (Default `{}`). Used for per-message details (e.g., token usage, model name, run ID).

### Indexing & Ordering Strategy
Chronological integrity is guaranteed at the database level:
- Composite Index: `ix_messages_conversation_created_at` on `(conversation_id, created_at, id)`.
- Retrieval Queries: Explicitly ordered by `ORDER BY created_at ASC, id ASC`. Secondary ordering by primary key `id` guarantees deterministic tie-breaking.

### Deletion Policy: Foreign Key Cascade
`messages.conversation_id` enforces `ondelete="CASCADE"`. When a conversation is deleted, all associated messages are atomically removed by the database engine. This prevents orphaned messages.

## 3. Layered Responsibility Boundaries

The conversation domain follows Sutra's layered architecture:

```text
HTTP Controller: apps/api/api/v1/routes/conversations.py
       │
       ▼
Application Service: apps/api/services/conversation.py (ConversationService)
       │
       ▼
Persistence Layer: apps/api/repositories/ (ConversationRepository, MessageRepository)
       │
       ▼
Database: PostgreSQL 16 (via SQLAlchemy async session)
```

1. **Routes (`apps/api/api/v1/routes/conversations.py`)**:
   - Handles HTTP queries, status codes (201, 200, 404, 422), and Pydantic serialization.
2. **Service (`apps/api/services/conversation.py`)**:
   - Enforces business rules: rejects empty/whitespace content (`ValidationError` -> 422), validates existence of conversations before message creation (`NotFoundError` -> 404), enforces pagination limits.
3. **Repositories (`apps/api/repositories/`)**:
   - Encapsulates queries (`select`, `limit`, `offset`, `order_by`). Never handles HTTP or business validation.

## 4. Planned Translation Boundary: Message to LLMMessage

When the Agent Runtime (Phase 5) consumes conversation history, it must convert durable domain messages into provider-neutral LLM contracts without coupling the persistence layer to the LLM layer:

```text
apps/api/db/models/conversation.py (Message)
                │
                ▼ [Translation / Adapter Boundary]
packages/agent_core/llm/models.py (LLMMessage)
                │
                ▼
packages/agent_core/llm/models.py (LLMRequest)
```

### Translation Rules:
1. `Message.role` (`user`, `assistant`, `system`) maps 1:1 to `LLMMessageRole`.
2. `Message.content` maps directly to `LLMMessage.content`.
3. Database attributes (`id`, `created_at`, `conversation_id`, database metadata) are stripped to avoid polluting model prompts.
4. Additional system prompts or dynamic context directives are injected as prepended `LLMMessage(role=LLMMessageRole.system, content=...)` elements inside the `LLMRequest`.

*(Note: This translation boundary will be implemented within the Agent Runtime service orchestration, preserving the independence of both domains).*
